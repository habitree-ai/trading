# 매매 진단 — 회차 운영 규칙

과거 거래에서 "무엇이 잘못됐나"를 찾아 회차를 거듭하며 정교하게 만드는 체계다.
화면은 `/diagnosis`, 데이터는 `okx-diagnosis.json`, 생성기는 `re_sys/diagnose.mjs`.

이 문서가 **정본**이다. 화면의 설명이 이것과 어긋나면 이 문서가 옳다.

---

## 0. 이 진단이 답하려는 것

> 4,000건 넘게 거래하고 −$42,819 를 잃었다. **무엇을 고쳐야 하는가.**

성공 정의는 "손실 원인을 찾는 것"이 아니다. 원인 후보는 이미 넘친다 —
기존 복기 리포트만 해도 실패 6분류와 행동 태그 28종을 세고 있었다.
**성공 = 그 후보들 중 무엇이 진짜이고 무엇이 착시인지 가르는 것.**

실제로 첫 회차가 답한 것이 그 착시였다: 기존 리포트의 1위 문제
`역추세 진입 → 추세 지속`(−56,273)은 승패 무관하게 다시 재면 차이가 **+0.04** 다.
3년째 1위로 보고 있던 것이 원인이 아니었다.

## 1. 파이프라인

```
OKX ──► manual-fetch.mjs ──► manual-trades.json      (M1, 로컬)
                              manual-fills / bills
        manual-archive.mjs ─► bills-archive/          (M0, 분기 원장 복원)
                                    │
                              manual-analyze.mjs      (M2, 로컬)
                                    │  실패 분류·진입 의도·MFE/MAE
                                    ▼
                              manual-review.json      45MB · gitignore
                                    │
                              diagnose.mjs            (M5, 이 문서)
                                    ▼
                    docs/diagnosis/okx-diagnosis.json ~100KB · 커밋
                                    │
                              src/lib/okx-diagnosis.ts
                                    ▼
                              /diagnosis
```

**원본은 커밋하지 않고 집계본만 커밋한다.** 45MB 를 저장소에 넣을 수 없고, 넣더라도
정본이 둘이 된다. 집계본은 정적 import 라 `next.config.ts` 의
`outputFileTracingIncludes` 를 건드릴 필요가 없다(그 설정은 런타임에 파일을 읽는
`/lab` 전용이다).

### 실행

```bash
node re_sys/manual-fetch.mjs                        # 새 거래 수집
node re_sys/manual-analyze.mjs                      # 분류·경로 재계산
node re_sys/diagnose.mjs --round "이번 회차의 질문"    # 발견 산출
```

`--round` 를 주지 않으면 직전 회차의 질문을 그대로 이어 쓴다.

## 2. 불변식 — 어기면 진단이 진단이 아니게 된다

### 가. 집계본은 **입력만** 담는다

`okx-diagnosis.json` 에 들어가면 **안 되는 것**: `lift`, `mean`, `sd`, `se`, `t`,
`confidence`, `severity`, `rank`, `winRate`, `held`.

들어가는 것: `n`, `wins`, `losses`, `sumNet`, `sumSqDev`, `sumWin`, `sumLoss`,
`sumFee`, `sumFunding`, `sumGross`, 그리고 기간 반쪽의 같은 값들.

이유: 문턱을 고쳤을 때 **보존된 과거 회차까지 같은 기준으로 다시 매겨져야** 추이가
거짓이 되지 않는다. 등급을 집계본에 박으면 회차마다 다른 자로 잰 값이 한 표에 섞인다.
`docs/kelly/okx-kelly.json` 이 켈리 값을 담지 않는 것과 같은 이유다.

### 나. 원시 합계로 줄 세우지 않는다

손실 총액이 큰 칸은 대개 **거래가 많았을 뿐**이다. 실측: `방향 뒤집기(≤10분)` 는 원시
합계 −19,047 로 2위지만 기준선 대비 차이는 −2.76 이고 승률 차이는 +0.3%p 다.
모든 순위는 `리프트 × n`(귀속 금액)에 등급 가중치를 곱해 세운다.

### 다. 결과로 정의된 라벨을 발견으로 세지 않는다

`manual-analyze.mjs:144` 는 `pnlUsd >= 0` 이면 `null` 을 반환한다 — **실패 분류 6종
전부가 패배 거래에만 붙는다.** 승률 0%는 결과가 아니라 정의다.

그런 축에는 `tautological: true` 와 `twinId`(같은 술어를 승패 무관하게 다시 잰 축)를
단다. 화면은 둘을 나란히 보여 준다. 첫 회차 실측:

| 손실 전용 라벨 | 정직한 쌍둥이 | 차이 |
|---|---|---|
| 이익 반납(청산 실패) −34.63 | 평가익 30% 도달 | **+38.23** |
| 손절 부재 −46.10 | 역행 50% 감내 | **+21.55** |
| 역추세 진입 −28.68 | 역추세 의도 | **+0.04** |
| 돌파 추격 −24.87 | 추격 의도 | **+0.81** |

### 라. 경로 축의 차이를 효과로 읽지 않는다

보유시간·MFE·MAE 는 진입 뒤 가격이 만든 값이다. 크게 이긴 거래가 큰 평가익 구간을
지나간 것은 당연하므로, "평가익 100%를 넘기면 좋다"는 순환 논리다.
그런 축에는 `pathDependent: true` 를 달고 순위에서 빼며, **조건부 비율**로만 읽는다
("+20% 에 닿은 뒤에도 51%가 손실 마감").

### 마. 미래를 훔쳐보는 축을 쓰지 않는다

기존 `과잉거래일(하루 N건)` 태그는 그날이 몇 건으로 끝나는지를 세 번째 거래 시점에
이미 아는 것처럼 군다. `nthOfDay`(그날 몇 번째)로 대체했다.

## 3. 신뢰 등급

`src/lib/verdict.ts` 의 `gradeFinding` 이 정한다. 문턱을 바꾸려면 거기만 고친다.

| 등급 | 조건 |
|---|---|
| **확정** | `n ≥ 100` · `\|t\| ≥ 3` · 기간 앞뒤 부호 일치 · 동어반복 아님 |
| **유력** | `n ≥ 30` · `\|t\| ≥ 2` · 기간 밖에서 뒤집히지 않음 |
| **가설** | 나머지 전부. **버리지 않는다** |

`t = 리프트 ÷ 표준오차`, `표준오차 = sd ÷ √n`.

### 왜 t ≥ 3 인가 — 다중비교

한 회차에 150개 넘는 구간을 동시에 검정한다. 관행값 `|t| ≥ 2`(p≈0.05)를 쓰면
150 × 0.05 ≈ **7.5개가 우연히 통과**해 확정 목록의 상당수가 거짓이 된다.
`|t| ≥ 3` 은 p≈0.0027 이라 같은 검정 수에서 기대 오탐이 0.4개다.

이 원장의 거래당 손익 표준편차는 **122달러**이고 기준선은 −10.64 다 — 산포가 신호의
11배다. 그래서 눈으로 커 보이는 차이도 대부분 잡음 안쪽이다.

### 왜 부호 반전은 유력이 아니라 가설인가

검정하지 않은 것보다 **검정했고 떨어진 것**이 못하다. 앞뒤 절반의 부호가 다르면 그
발견은 찾은 구간 안에서만 참이었다.

## 4. 코호트 — 기준선이 하나면 마진 축이 통째로 틀린다

| 코호트 | 조건 | n | 거래당 |
|---|---|---|---|
| `all` | 청산 거래 전부 | 4,023 | −10.64 |
| `lever` | `lever` 기록됨 | 2,952 | −12.19 |
| `margin` | `lever` + 가격 경로 | 2,942 | −12.19 |

아카이브 1,071건은 `lever` 가 비어 `manual-analyze` 가 `lever ?? 1` 로 계산한다.
그 거래들의 평균 손익(−6.37)이 나머지보다 5.8 높아, **마진 축을 전역 기준선에서 빼면
가짜 리프트 +1.55 가 전 축에 실린다.** 마진 파생 축은 반드시 `margin` 기준선에서 뺀다.

기간 반쪽도 마찬가지다. 앞 절반 −7.96 / 뒤 절반 −12.66 으로 4.7 이나 벌어져 있어,
통합 기준선으로 재면 **없던 안정성이 만들어진다.** 반쪽은 반쪽의 기준선과 견준다.

## 5. 회차 운영

### 언제 새 회차를 여는가

- **새 청산이 250건 이상** 쌓였을 때. 그 아래에서는 차이가 흔들리는 폭에 묻힌다.
- 또는 **축·문턱을 바꿨을 때** — `--round` 로 강제하고 무엇을 왜 바꿨는지 남긴다.

지문(`sourceFingerprint = 거래수:마지막청산시각`)이 같으면 회차를 늘리지 않는다.
코드만 고치고 다시 돌렸을 때 이력이 부풀지 않게 하기 위해서다.

보존은 최근 **12회차**. 그 이전은 git 이 들고 있다.

### 읽는 순서

1. **회차별 변화** — 지난 회차의 확정이 이번에도 확정인가. 내려갔으면 발견이 아니었다
2. **확정된 것** — 행동을 바꿔도 되는 자리는 여기뿐
3. **손실의 갈래** — 진입이 틀린 몫과 나오지 못한 몫
4. **사각지대** — 문제로 세고 있던 것 중 원인이 아니었던 것

### 발견을 「해결」로 옮기는 기준 — 둘 다 참일 때만

1. 차이가 흔들리는 폭 안으로 들어왔다
2. **그 구간의 거래 수가 줄었다** — 피했다는 증거

거래 수가 그대로인데 차이만 줄었다면 고친 게 아니라 흔들린 것이다.
한 회차만 좋아진 것도 해결이 아니다.

### 사람이 "해결"을 누르는 버튼은 만들지 않는다

발견은 데이터가 해결하지 사람이 해결하지 않는다. 그 버튼이 곧 자기기만 장치다.

## 6. 원칙으로 옮기기 — 고리가 닫히지 않는 지점

진단은 re_sys 의 4,023 포지션을 보고, 원칙 체크는 앱 DB `trades` 행에 붙는다.
두 표를 잇는 열쇠 `trades.okx_pos_id` 가 채워진 행은 11개뿐이다.

**따라서:**

- 원칙을 등록해도 **과거 거래에 체크가 자동으로 생기지 않는다**
- 다음 회차 진단은 `trade_principle_checks` 를 **읽지 않는다**
- 원칙은 북에 매여 있고, `/diagnosis` 는 북 선택이 없는 영역이다

**닫히는 것은 여기까지다** — 진단이 규칙을 만들고, 앞으로 손으로 적는 거래에서 그
규칙을 판단하고, **다음 회차 원장의 숫자가 달라졌는지**로 확인한다.
체크 기록이 아니라 원장의 숫자가 증거다.

씨앗 버튼은 `확정` 등급과 조건부 청산 발견에만 붙인다. 확정되지 않은 것을 원칙으로
만들면 지키느라 잃는 쪽이 커진다.

`principles.detail` 마지막 줄에 `발견 id \`...\`` 마커를 남긴다 — 제목을 고쳐 써도
어느 발견에서 왔는지 되짚을 자리가 그 줄뿐이다.
