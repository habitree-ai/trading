# 트레이딩 누적기록

캡쳐를 올리면 거래가 **데이터화 → 누적 → 대시보드**로 이어지는 매매일지.
데이터 항목과 지표 체계는 2024년부터 운영해 온 **구글시트 매매일지**를 정규화한 것이다.

## 왜 만드는가

기존 시트는 탭(= 계좌/기간별 일지)마다 컬럼이 다르게 진화했고, 계산값을 셀에 박아둔 탓에
`#REF!`·`#VALUE!`로 깨진 곳이 많다. 이 프로젝트는 같은 항목 체계를 정규화된 스키마로 옮기고,
**원자값만 저장하고 파생지표는 전부 계산**해서 그 문제를 구조적으로 없앤다.

## 계정별 관리

거래소 API 키는 원래 `.env`에 한 벌뿐이었다. 그래서 **누가 로그인하든** 동기화를 켜면 같은
OKX 계정을 긁어 왔고, 그 사실을 `books.okx_sync_enabled`에 "사용자당 하나만" 유니크를 걸어
덮어 두고 있었을 뿐이다. 계정이 둘 이상 되는 순간 남의 거래가 내 일지에 쌓이는 구조였다.

지금은 사람마다 자기 키를 등록한다.

```
exchange_accounts (사용자 × 거래소 = 1행)
  ├─ label                한눈에 구분할 꼬리표
  └─ *_secret_id (uuid)   Vault 비밀 참조 — 키 원문은 이 표에 없다
        ↑
books.exchange_account_id  ─ 복합 FK (id, user_id) → 남의 계정은 붙지 않는다
                           ─ 부분 유니크 → 한 계정은 북 하나에만
```

- **키 원문은 DB 표에 없다.** Supabase Vault가 암호화해 보관하고 표에는 비밀의 uuid만 남는다.
- **복호화는 `service_role` 전용**(`public.okx_credentials()`)이다. authenticated에게 열어 두면
  브라우저에 세션이 있는 역할이라 XSS 한 번에 거래소 키가 통째로 새 나간다.
  그래서 동기화에는 `SUPABASE_SECRET_KEY`가 **필수**다.
- **북과 계정은 1:1**이다. 같은 계정을 두 북에 붙이면 같은 거래가 양쪽에 들어가 자금 곡선이
  두 배로 부푼다 — 부분 유니크 인덱스가 둘째를 막는다.
- **계정을 지우면 Vault 비밀도 함께 지운다**(after delete 트리거). 안 그러면 아무도 참조하지
  않는 키가 복호화 가능한 채로 남는다.

### 동기화는 보고 있는 북을 받는다

`OkxSyncButton`은 대시보드와 거래 목록 양쪽에 있다. 눌렀을 때 받아 오는 건 **활성 북**
(쿠키 `active_book`, 없으면 첫 북)이다 — 화면이 그리는 북과 같아야 버튼을 누른 자리에서
숫자가 채워진다.

예전에는 "거래소 계정이 붙은 북"을 조건 없이 하나 집어 왔다. 그래서 계정이 붙은 북이
둘 이상이면 그 쿼리(`.maybeSingle()`)가 에러를 내 동기화가 통째로 실패했고, 하나여도
지금 보고 있는 북과 다를 수 있었다. 고르는 규칙은 `resolveSyncTarget()`에 따로 떼어 뒀다.

활성 북에 계정이 없으면 계정이 붙은 다른 북으로 넘어가지 않고 멈춘다 — 화면에 없는 북을
말없이 건드리는 것보다 어느 북이 비었는지 짚어 주는 게 낫다.

동기화가 끝나면 `revalidatePath("/", "layout")`으로 되돌린다. 대시보드는 동적 렌더라
성과 요약·자금 곡선·KPI가 모두 새 거래를 반영해 다시 계산된다.

### 로그인 허용 계정

구글 로그인의 기본값은 "구글 계정이 있으면 누구나"다. 이 앱은 한 사람의 매매 기록과 거래소
API 키를 담으므로 `ALLOWED_EMAILS`에 적힌 주소만 통과시킨다. 세 겹으로 건다.

| 지점 | 역할 |
|---|---|
| `/auth/callback` | 로그인 직후 판정 — 세션을 실제로 지우는 건 여기뿐(라우트 핸들러라 쿠키를 쓸 수 있다) |
| `proxy`(미들웨어) | 모든 페이지 차단 → `/login?error=forbidden` |
| `requireUser()` | 데이터에 닿기 직전의 마지막 방어선 |

비워 두면 제한하지 않는다 — 로컬에서 아무 계정으로나 붙어 보기 위해서다. 배포에는 반드시 채울 것.

## 중복 등록 차단

같은 거래를 두 번 넣으면 손익이 두 배로 잡힌다. 실제로 전달받은 캡쳐 중
`IMG_5084`와 `IMG_5087`은 폰 시계만 다른 **동일 거래**였고, `IMG_5083`은 그 거래의
청산 주문을 파고든 화면이었다. 화면만 봐서는 구분이 안 되고 **주문번호로만** 알아볼 수 있다.

`trade_fills.order_no`에 주문번호를 남기고 `(user_id, order_no)`에 유일 색인을 걸어,
저장 전에 이미 있는 주문인지 확인한다. 걸리면 어느 거래와 겹치는지 알려 주고 멈춘다.

## 캡쳐 추출

```
캡쳐 선택 → Storage 업로드(원본 먼저 보존) → 브라우저 OCR(Tesseract, eng)
  → 거래소 어댑터 파싱 → 신뢰도 ≥ 0.75 면 폼 프리필
  → 아니면 /api/extract 로 AI 비전 재시도 → 폼 프리필
  → 확인이 필요한 칸은 테두리 강조 + 안내 문구
```

지원 거래소: **OKX**. 화면 두 종류를 각각 다룬다.

| 어댑터 | 화면 | 비고 |
|---|---|---|
| `okx-position.ts` | `Position details` + `Order history` | **권장** — 진입·청산이 한 장에 있어 거래가 완성된다 |
| `okx.ts` | `Order details` | 주문 1건. 청산 캡쳐면 진입 정보가 없다 |

새 거래소는 `ExchangeAdapter`를 구현해 `src/lib/extract/index.ts`의 `ADAPTERS`에 추가한다.

OKX 화면을 다루며 부딪힌 함정들 — 전부 테스트로 고정해 뒀다:

- **`Filled`는 수량이 아니라 USDT 금액이다.** 분할 체결 평균가를 단순평균으로 내면 틀린다.
  `Σ금액 ÷ Σ(금액/가격)`(수량가중)이어야 손익 검산이 맞는다.
- **`Close short` 배지가 초록, `Open short`가 빨강이다.** 롱과 색이 뒤집히므로 **색으로 방향을 판단하면 안 된다.**
- **`Closed`가 `--`면 포지션이 아직 열려 있다**(부분청산). 확정 거래로 기록할지 사람이 정해야 한다.
- **`Closed`·`Closed PnL`·`Closed (USDT)`가 같은 접두사를 쓴다.** 라벨 매칭이 서로를 가로챈다.
- **`Close long` 주문 캡쳐엔 진입 정보가 없다.** 폼이 그 사실을 안내한다.
- **`₮`는 테더 기호다.** 원화(`₩`)로 오인하면 통화 파싱이 깨진다.
- **`Creation time`엔 연도가 없다.** 연도가 붙은 타임스탬프를 우선 쓰고, 없으면 가정했다고 알린다.
- **`Order price` ≠ `Fill price`.** 실제 체결가인 후자를 쓴다.
- **`Closed PnL`과 `Closed PnL%`는 다른 값이다.**
- **`Closed (USDT)`는 청산된 부분의 진입 기준 원가**다. 청산 체결액이 아니고,
  부분청산이면 진입 합계보다 작다. 거래의 규모는 실제로 닫힌 만큼이어야 한다.
- **상단 요약은 두 칸이 한 줄에 붙는다.** `Realized PnL (USDT) Closed (USDT)` 다음 줄에
  값 두 개가 나란히 온다 — 라벨 옆에서 값을 찾으면 `(USDT)`를 집어 조용히 실패한다.
- **OCR이 흘리는 글자**: `PnL`→`PrL`, `Long`→`Loc`, `₮`→`¥`, `--`→`-`.
  그래서 테스트 픽스처는 다듬은 텍스트가 아니라 **실제 OCR 원문**을 쓴다.

### 체결액 불변식

캡쳐 3장에서 모두 성립을 확인한 항등식으로 손익을 되짚는다.

```
롱: 손익 = 청산 체결액 − 청산분 원가
숏: 손익 = 청산분 원가 − 청산 체결액   (먼저 팔고 나중에 되사므로 뒤집힌다)
```

가격·수량을 거치지 않아 OCR이 자릿수를 밀면 바로 드러난다.

## 당시 차트 (OKX 공개 시세)

거래 상세 화면에서 **진입·청산 시점의 실제 캔들**을 되짚는다. OKX `/api/v5/market/history-candles`는
인증이 필요 없고, `/api/candles` 라우트로 프록시해 CORS를 피하고 하루 캐시한다.

> **캔들에는 3개월 제한이 없다.** 거래내역(`positions-history`)만 3개월치를 준다.
> 실제로 확인한 결과 `history-candles`는 **2년 전 15분봉까지** 정상적으로 돌려준다
> (2024-08 구간 100건 확인). 그래서 캔들을 DB에 쌓아 두는 캐시 테이블은 두지 않았다 —
> 거래소가 원본을 계속 갖고 있는데 사본을 관리하면 용량과 정합성만 늘어난다.

### 페이지는 미리 계산해 한꺼번에 받는다

OKX는 **요청당 100개**만 준다. 예전에는 응답을 보고 다음 `after` 커서를 정했는데, 그러면
페이지 수만큼 왕복이 **순서대로** 쌓인다. 그래서 상한을 12페이지로 묶어 뒀고, 15분봉으로
2주짜리 거래를 보면 진입 지점에 닿기도 전에 잘렸다.

봉 간격이 고정이라 커서는 계산으로 나온다 — `after = to − n × (봉간격 × 100)`.
미리 알면 한꺼번에 띄울 수 있으므로, 상한을 **40페이지(4000봉)**로 올리고 8개씩 묶어
동시에 받는다(OKX 공개 시세는 IP당 20회/2초라 그 절반). 15분봉이면 41일치여서
한 달 넘게 들고 있던 거래도 진입까지 닿는다.

실측으로 이음매를 확인했다 — 15분봉 6페이지에서 고유 캔들 600개, **중복 0 · 틈 0**.
빠진 봉이 있는 구간에서는 페이지가 겹치거나 덜 오는데, 받은 캔들을 시각으로 묶어 담으므로
겹침은 저절로 지워지고 빈 곳은 그냥 비어 온다.

차트 엔진은 **TradingView가 공개한 `lightweight-charts`**다. 십자선·확대·이동·축 드래그가
트레이딩뷰와 같은 조작감으로 동작한다.

- **진입~종료** — 거래 길이에 맞는 봉을 자동 선택(구간이 60봉 안팎이 되도록)
- **앞뒤 60봉** — 어느 보기든 거래 구간 양옆에 60봉씩 더 붙인다. 거래 구간이 화면 가운데
  1/3에 놓여, 직전 추세와 청산 뒤 움직임까지 한 화면에서 읽힌다.
- **15분봉 ~ 일봉** — 고정 배율로 당시 시장 맥락을 본다
- 체결은 ▲진입 / ▼청산 마커, 손절가·평균가는 축 라벨이 붙은 가로선
- **📏 측정** — 트레이딩뷰의 자 도구. 끌면 두 지점 사이의 **가격 변화·비율·기간·봉 개수**를 잰다

> 시간축과 십자선 라벨은 `Asia/Seoul`로 찍는다. 라이브러리 자체는 타임존을 모르고 UTC로
> 표기하므로 `tickMarkFormatter`로 눈금을 직접 만든다. 다만 **날짜 구분 눈금의 위치는
> UTC 자정 기준**이라 장중 차트에서 `27일` 표시가 KST 자정이 아닌 곳에 놓인다(라벨 자체는 맞다).

측정 도구의 계산부는 `src/components/measure-tool.ts`에 순수 함수로 분리해 두었다 —
드래그 방향과 무관하게 같은 값이 나오고, 봉 개수는 양 끝을 포함한다.

### 평균가는 점으로 찍지 않는다

분할 체결이면 `entry_price`/`exit_price`는 **가중평균가**다. 평균가는 어느 한 시점의
가격이 아니어서 그대로 점으로 찍으면 캔들 밖으로 떠오른다 — 실제로 청산 평균 65,265가
그 시각 캔들 고가 65,063보다 **202 위**에 찍혀 차트가 틀린 것처럼 보였다.

그래서 낱개 체결을 `trade_fills`에 남기고 차트는 **실제 체결 좌표**에 점을 찍는다.
평균가는 가로 점선으로만 표시한다. 체결 기록이 없는 수동 입력 거래는 진입가가 곧
그 시점의 가격이므로 종전대로 한 점씩 찍는다.

## 지표 산식

시트 수식을 역산해 3개 탭에서 일치를 확인했다.

```
승률       = 승 / (승 + 패)
평균수익   = mean(pnl > 0),  평균손실 = mean(|pnl < 0|)
손익비     = 평균수익 / 평균손실
이익기대치 = 승률 × 손익비
손실기대치 = 패률
기대치값   = 이익기대치 − 손실기대치     ← R 단위 기대값
누적 최고치 = running max(자금),  MDD = min((자금 − 최고치) / 최고치)
차액       = 최종자금 − 초기자금 + 출금누계
```

`손익비`는 시트 탭마다 수식이 달랐으나(7.62 / 12.57 / 12.79 …) **표준 payoff ratio
(평균수익 ÷ 평균손실)로 확정**했다.

### 비용은 지표에 포함되고, 성격별로 나뉜다

돈 계산은 전부 `net = 손익 + 거래 수수료 + 펀딩비`로 한다. OKX가 `Realized PnL`로
부르는 값이고, `pnl`(`Closed PnL`)은 비용 이전 총액이다. 100배 레버리지에서 수수료는
손익의 10%에 육박해, 빼먹으면 자금 곡선도 손익비도 실제보다 좋게 나온다.

`fee`(거래 수수료 = 체결 비용)와 `funding_fee`(펀딩비 = 보유 비용)는 나눠 담는다.
합쳐 두면 "오래 들고 있어서 샌 돈"을 따로 볼 수 없다.

### 성과 요약 — 값마다 "언제"가 붙는다

KPI 타일은 지금 상태가 어떤지를 한눈에 보여 준다. 성과 요약 표는 거기 없던 걸 채운다 —
최대 손실이 **언제** 났는지, 낙폭이 **어느 구간**이었는지. 시점을 모르면 그때 무슨 일이
있었는지 되짚을 수 없다.

기준 단위가 거래 건이 아니라 **거래일**이다. 하루에 다섯 번 들어갔다 나온 날의 성적은
그날 합계로 판단해야 한다 — 건별로 세면 스캘핑이 잦은 날이 통계를 통째로 끌고 간다.
그래서 이 표의 승률은 KPI 타일의 건 기준 승률과 값이 다르다.

```
총거래일        = 청산된 거래가 있었던 날의 수
승률(일)        = 이익일 ÷ (이익일 + 손실일)
손익 (P/F)      = 총수익 ÷ |총손실|
보상 비율 (ROA) = 총손익 ÷ |최대 낙폭 금액|
하루 최대 수익  = max(날별 손익 합계)     ← 거래 1건이 아니라 그날 합계
최대 연속 이익  = 이익일이 연달한 최대 일수
```

**ROA**는 "한 번 견뎌야 했던 최악의 낙폭에 견줘 얼마를 벌었나"다. 수익률만 보면 낙폭을
얼마나 크게 물고 갔는지가 지워진다.

연속 일수는 **거래가 없는 날을 건너뛴다.** 12거래일 연속이어도 달력으로는 26일에 걸칠 수
있다. MDD 구간은 자금 곡선을 새로 재지 않고 `deriveTrades`가 이미 잰 낙폭을 그대로 훑으며
고점이 갱신된 시점만 따로 기억한다 — 다시 재면 KPI 타일의 MDD와 값이 갈린다.

### 벤치마크 — 그냥 들고만 있었어도

자금 곡선이 올랐다는 것만으로는 잘한 건지 알 수 없다. 시장 전체가 두 배가 된 구간에서
30% 벌었다면 그건 진 것이다. 같은 기간 BTC 시세를 **우축**에 겹쳐 그린다.

가로축이 시간이 아니라 **거래 순서**라, 벤치마크도 시계열 그대로가 아니라 각 거래 시점의
값으로 찍어야 두 선이 같은 자리를 가리킨다. 거래마다 그 시각이 속한 일봉을 이분 탐색으로
찾는다. 시세를 못 받아 오면 그 선만 빠지고 나머지는 그대로 그려진다 — 거래소가 흔들렸다고
대시보드 전체가 깨지면 안 된다.

받아 올 구간의 끝은 `lastActivityAt()` — 목록의 마지막 거래가 아니라 **가장 늦은 청산**이다.
거래 목록은 진입순이라(`deriveTrades`) 먼저 들어가 나중에 나온 포지션이 있으면 그 청산이
목록 끝보다 뒤에 온다. 목록 끝으로 자르면 그 뒤 거래들이 시세 구간 밖으로 밀려 마지막
종가가 그대로 이어진 채 찍힌다 — 동기화로 겹치는 포지션이 한꺼번에 들어올 때 잘 어긋난다.

캔들은 URL 단위로 하루 캐시한다. 커서가 구간 끝에서 역산되므로 동기화로 새 거래가 들어오면
커서가 통째로 밀려 자동으로 다시 받아 온다 — 동기화 사이에는 그대로 캐시를 탄다.

### 출금은 자금이 줄어든 게 아니다

잔액 곡선 하나만 보면 오른 게 잘 벌어서인지 돈을 더 넣어서인지, 내린 게 잃어서인지
뽑아 가서인지 구분되지 않는다. 그래서 대시보드는 두 선을 겹쳐 그린다.

| 계열 | 정의 | 읽는 법 |
|---|---|---|
| **실제 잔액** (실선) | `equity_after` — 이체 반영 | 거래소에 지금 있는 돈 |
| **매매 성과** (점선) | `초기자금 + Σ realized_pnl` | 넣고 뺀 돈을 걷어낸 실력 |

두 선의 간격이 곧 외부에서 드나든 돈이다. 출금이 일어난 지점은 잔액 곡선 위에
**주황 점**으로 찍고, 아래에 **누적 출금**을 계단형으로 따로 그린다 — 출금은 특정 시점에
한 번씩 일어나는 사건이라 부드럽게 이으면 없던 날에도 빠져나간 것처럼 보인다.

출금으로 세는 건 **거래계좌에서 나간 이체**(음수 `transfer`)와 시트의 `출금`뿐이다.
온체인 출금은 자금계좌에서 나가므로 곡선과 시점이 어긋나 여기 세지 않는다.

```
거래계좌 출금 누계 = Σ|transfer < 0| + Σ trades.withdrawal
```

`순이체`와 다른 값이다. 100을 넣고 100을 뺐으면 순이체는 0이지만 뽑아 간 돈은 100이다 —
자금 곡선이 얼마나 깎였는지는 출금 누계로만 읽힌다.

### 손익 교차검증

`crossCheckPnl()`이 `투입 × (청산가 − 진입가) / 진입가 × 방향`으로 손익을 되짚어
입력값과 대조한다. 부호가 반대거나 25% 넘게 어긋나면 저장 전에 경고한다.
OCR이 자릿수를 밀거나 방향을 반대로 읽는 사고를 여기서 잡는다.

## 색 규칙

손익의 적/녹은 거래소 캡쳐와 색을 맞추기 위한 선택이다. 적녹색약에게 두 색은 구분되지
않으므로(검증 결과 ΔE 3.3), **0선 기준 막대 방향 · 항상 표기되는 `+`/`−` 부호 · 승/패 텍스트 배지**로
이중 인코딩해 색 단독에 의존하지 않는다.

### 환경변수 키에서 계정별 키로 옮기기

`.env`에 있던 OKX 키를 계정에 옮기는 절차다. **순서가 있다** — 시드 스크립트가
`okx_sync_enabled`를 읽어 새 연결로 옮기고, 그다음 마이그레이션이 그 컬럼을 지운다.

```bash
# 1) supabase/migrations/0010_exchange_accounts.sql 적용
#    (cdhrich@gmail.com 계정이 auth.users 에 있어야 한다 — 없으면 멈춘다)
npm run seed:okx-account     # 2) 키 → Vault, 기존 동기화 북 → 새 계정 연결
# 3) supabase/migrations/0011_drop_okx_sync_enabled.sql 적용
# 4) .env 에서 OKX_API_KEY / OKX_API_SECRET / OKX_API_PASSPHRASE 삭제
```

이후 키 등록·교체·삭제와 북 연결은 앱의 **설정** 화면에서 한다.
