# 운영 절차 — 승격 사다리와 일상 점검

## 승격 사다리 (건너뛰지 말 것)

| 단계 | 모드 | 리스크 | 승격 조건 | 폐기 조건 |
|---|---|---|---|---|
| 1 | **페이퍼** (`--mode paper`) | — | 2~4주 무사고 운전: 신호·체결 시뮬·기록이 기대대로 | 판정 불일치 발견 시 원인 규명 전 진행 금지 |
| 2 | **데모** (`--mode demo`) | 10% | 4~6주: 주문·브래킷·시한 청산이 거래소에서 기대대로 동작 | API 오류·리컨실 경고 반복 |
| 3 | 라이브 | **2%** | 신규 20~30건 후 기대값 > 0 · P/F ≥ 1.0 | 백테스트 MDD(리스크 환산) 초과 시 즉시 |
| 4 | 라이브 | **5%** | 3단계와 같은 조건을 다시 충족 | 동일 |
| 5 | 라이브 | **10%** (쿼드 공격형) | MDD −72%를 견딘다는 자금·심리 증명 | 동일 |

- 파라미터를 하나라도 바꾸면(`config.mjs`) **그 단계의 시계는 처음부터 다시** 돈다.
- 월 7.5건 페이스로 20~30건 = **약 3~4개월/단계**. 단축하고 싶은 유혹이 곧 위험이다.

## 실행

```
# 0) 키 검증 — 주문 없이 읽기 전용. 키 유형(라이브/데모)·권한·포지션 모드·잔고를 확인한다.
node --env-file=.env.local system-trading/bot/check-keys.mjs

# 페이퍼 (키 불필요)
node system-trading/bot/run.mjs --loop

# 데모 — 준비 2가지: ① OKX 웹 > 모의거래에서 데모 API 키 발급 → .env 에 기입
#                    ② OKX 거래 설정 > 포지션 모드를 "롱/숏 모드"로 (봇이 시작 시 검사한다)
copy system-trading\bot\.env.example system-trading\bot\.env   (직접 편집)
node --env-file=system-trading/bot/.env system-trading/bot/run.mjs --mode demo --loop
# --mode demo / --mode=demo 어느 쪽도 되고, 시작 로그 첫 줄이 현재 모드를 보여 준다.

# 1회 실행(외부 스케줄러용) — Windows 작업 스케줄러에 4시간 주기 등록 가능
node system-trading/bot/run.mjs --once 는 기본 동작(플래그 불필요)
```

- 봇은 4H 봉 마감(UTC 0·4·8·12·16·20시) 90초 뒤에 돈다. 일봉 기준(④)은 새 마감 봉
  감지로 같은 사이클에서 처리된다.
- **PC가 꺼져 있으면 봉을 놓친다.** 놓친 봉들은 다음 실행에서 평가·기록되지만("missed")
  **진입은 최신 마감 봉의 신호로만** 한다 — 몇 시간 지난 신호를 지금 가격에 사는 건 다른
  전략이다. 상시 운영은 항상 켜진 머신(미니PC·VPS)에서. 열린 포지션의 손절·목표는
  거래소 브래킷이 지키므로 봇이 꺼져도 보호는 유지된다(시한 청산만 지연됨).
- **아주 소액 계좌 주의**: 잔고×레버리지가 최소 주문 명목(BTC-USDT-SWAP 기준 수 달러)에
  못 미치면 진입이 "사이징 불가"로 건너뛴다 — 리스크를 키워 채우지 않는 것이 의도된 동작이다.

## 서버 사이클 (n8n → /api/cron/quad)

집 PC 의 작업 스케줄러는 PC 가 자면 봉을 통째로 놓쳤다(2026-08-18~20 나흘간 4봉).
그래서 사이클을 배포된 앱의 라우트로 옮기고, 호출은 n8n 스케줄이 한다.

```
n8n Schedule (UTC 2 */4 * * *)  →  POST /api/cron/quad?mode=live
    헤더: authorization: Bearer $CRON_SECRET
          x-vercel-protection-bypass: <Vercel 자동화 우회 시크릿>
```

- **도는 코드는 같다.** 라우트가 `bot/engine.mjs` 를 그대로 부른다 — 판정·사이징·주문
  경로는 로컬 실행기와 한 줄도 다르지 않다. 바뀐 것은 실행 위치뿐이다.
- **게이트는 `system_state.live_enabled`.** 환경변수(LIVE_TRADING_ACK)는 서버에 올리는
  순간 상시 켜짐이 되어 잠금 구실을 못 한다. 시스템 화면 우상단 킬스위치가 그 손잡이다.
- **잠금은 `system_state.locked_until`.** 두 실행기가 겹쳐도 한쪽만 돈다. 그래도
  로컬 작업 스케줄러는 꺼 두는 것이 맞다 — 잠금은 안전망이지 설계가 아니다.
- **계좌는 `OKX_EXPECTED_UID` 가 못 박는다.** uid 가 다르면 주문 없이 409 로 멈춘다.
- `?probe=1` — 주문 없이 키·uid·포지션 모드·잔고만 확인한다. 킬스위치가 꺼져 있어도 통과한다.

배포 환경에 필요한 변수: `OKX_API_KEY` · `OKX_API_SECRET` · `OKX_API_PASSPHRASE`(봇 서브계정) ·
`OKX_EXPECTED_UID` · `SYSTEM_BOT_USER_ID` · `SUPABASE_SECRET_KEY` · `CRON_SECRET`.

전환 순서(순서가 안전이다):
1. 환경변수를 넣고 배포한다 → `?probe=1` 로 계좌가 맞는지 본다(주문 없음).
2. 로컬 작업 스케줄러 `QuadBotLive` 를 끈다.
3. 화면에서 킬스위치를 켠다.
4. n8n 워크플로를 활성화한다.

## 일상 점검 (하루 1회, 1분)

정본은 `data/*.jsonl` 파일이 아니라 앱 화면이다(본대는 Supabase 에 쓴다). 시스템 화면의
**운전 상태** 판이 아래를 한 번에 답한다 — 초록이 아닌 줄만 보면 된다.

1. 운전 상태 배지 — 정상 가동 / 지연 / 멈춤.
2. 최근 24시간 사이클 — `6/6회` 가 아니면 놓친 봉이 있다는 뜻이다.
3. 평가 봉 — "최신 봉까지" 가 아니면 캔들 조회가 막히고 있다.
4. 경고 — `수동 확인 필요` 류는 **그날 해결**한다.
5. 실주문 게이트 — 라이브가 "실주문 허용" 인지, 쉬는 중이면 "차단" 인지.

## 장애 대응

| 증상 | 대응 |
|---|---|
| API 오류로 사이클 실패 | 다음 사이클에 자동 재시도. 반복되면 키 권한·IP 화이트리스트 확인 |
| 브래킷 없음 + 포지션 존재 경고 | 거래소 앱에서 손절·목표 수동 재설정 후 state 파일 확인 |
| 진입 직후 봇 중단 | 주문 직후 state 를 즉시 저장하므로 재시작하면 이어서 관리된다. 단 "미추적 포지션" 경고가 뜨면 주문·저장 사이에 죽은 것 — 거래소 화면과 state 를 수동 대조할 것 (브래킷 보호는 거래소에 살아 있다) |
| 봉 확정 지연 | 실행기가 2분 간격 2회 재시도. 그래도 놓치면 다음 사이클에 "missed"로 기록만 남고 진입하지 않는다 |
| 오래(4H 기준 수십 일) 꺼졌다 재시작 | 페이퍼: "진입 봉이 조회 창 밖" 경고 시 그 포지션은 수동 정리. 놓친 신호는 진입하지 않는 것이 정상이다 |
| state 파일 손상 | data/ 백업본으로 복구, 없으면 거래소 포지션 기준으로 수동 재작성 |

## 지켜야 할 것

- API 키 권한은 **거래만**. 출금 권한 금지. IP 화이트리스트 설정.
- `.env` 는 절대 커밋하지 않는다 (`.gitignore` 처리됨).
- 펀딩비는 모델 밖이다 — 월간 실현 손익과 거래소 명세를 대조해 실효 비용을 기록할 것.
- 실거래 성적은 `백테스트 원장` 흐름대로 회차 문서에 누적한다 — 그것이 승격 판정의 근거다.
